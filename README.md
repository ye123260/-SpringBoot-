## 演示流程

1. `manager`审核`pending`，审核前下单被禁止。
2. `user`浏览商家并进入菜单，选择菜品后点击“下单”；在支付页核对联系电话、选购商品和收餐地址，创建待支付订单并完成模拟支付；商家自动接单并进入制作中，`merchant`点击出餐完成、自取核销。

6. 管理员查看凭证与审计；社区人员只能查看本社区订单、审核归属或添加协助记录，不能代用户确认。

管理员登录入口：访问 `http://127.0.0.1:8081/admin`。管理员与用户使用不同主机名，浏览器会保存独立会话，可同时打开。普通入口不会显示最高管理员选项；后端仍独立校验ADMIN角色。数据库连接池事务隔离已显式设置为REPEATABLE_READ。

数据隔离规则：最高管理员可以查看全局订单与审计数据；普通用户的订单查询只返回本人订单，不能访问账户审批、审计、管理员配送维护等接口。后端角色校验是强制边界，前端隐藏不作为安全措施。

用户端设置提供“修改密码”：输入原密码、新密码、确认新密码，可切换显示密码。普通用户注册和修改使用独立易记规则（至少8个字符，支持中文短语，不强制大小写或符号，拦截部分常见弱密码）；其他角色新设密码为9～12位，并保留三类字符规则。普通用户密码最多64个字符且UTF-8编码不超过72字节，避免BCrypt输入截断。已有密码继续有效，后续新设或修改按新规则校验。独立PasswordService负责规则和BCrypt哈希，复用account.password_hash存储，不增加第二套账户或明文密码表。

保存密码后重新登录，服务器在每次鉴权时比对会话的凭据版本，旧会话失效；只修改当前账户，忽略客户端指定的目标ID或角色。修改入口受CSRF校验保护，原密码连续错误5次锁定15分钟，修改记录仅保留审计事件。已有密码继续有效，不批量重置。部署重启后原会话需重新登录。

## 社区居民名册（2026-10-16）

用户端社区工作人员（STAFF）和社区管理者（MANAGER）新增“居民名册”。只能访问本人所属社区；最高管理员可切换社区查看。普通用户、商家、骑手无名册访问权限，后端独立鉴权，不能靠更改communityId跨社区。

每个社区对应一张真实MySQL表：`community_resident_<社区ID>`，例如`community_resident_1`。社区ID仅取服务端认可的正整数，表名不接收上传文件或页面提供的字符串。由`CommunityRosterTables`统一建表，`CommunityRosterMigration`在启动时准备既有社区表并幂等同步已有普通用户；管理员创建新社区时同步准备表。业务账户需有本项目库的CREATE权限，应用不要求DROP权限。MySQL DDL使用独立连接完成，启动同步在建表后逐账户开启事务，避免隐式提交和旧快照读表定义冲突。

社区人员可下载Excel模板并上传`.xlsx`、`.xls`或`.csv`（UTF-8/GB18030），文件不超过2MB、每次不超过1000行，须单工作表。五列表头依次为：姓名、联系电话、详细收餐地址、常用联系人、常用联系人电话。姓名和11位手机号必填；常用联系人和电话一起填写；地址可后续补充。Excel公式拒绝导入。先校验完整文件，再在事务中写入；任何非法行整批不保存并提示行号。重复姓名和电话跳过，不覆盖旧资料；同社区导入用社区行锁串行，数据库唯一键兜底。

名单导入仅建立居民档案，不生成登录账户、密码或审核权限。新注册的普通用户（USER）选择社区后，其账户与该社区名册行在同一事务中提交，PENDING状态仍需原审核流程；名册读取当前账户审核状态。商家、骑手、社区工作人员不当作居民自动入册。用户修改个人资料时同步本人名册行，订单联系人快照保留原值。注册未填写的电话、地址在名册显示待补充。

导入档案不凭姓名或电话自动认领为登录账户，避免未核实身份造成错误绑定；因此同一居民先导入、后注册时会保留两条不同来源记录，目前不提供自动合并，必须由社区工作人员人工核验后合并。导入去重仅作用于导入行及已有相同姓名电话的行，不代表完成居民身份核验。

接口：GET `/api/community/residents`（分页、姓名/电话搜索；ADMIN显式选择communityId）、GET `/api/community/residents/template`、POST `/api/community/residents/import`（multipart字段file、CSRF必需）。个人资料同步复用原/profile接口，不开放任意账户ID写入。

验证记录：`docs/community-residents-browser-results.log`、`target/surefire-reports/cn.community.meal.CommunityRosterTest.txt`；部署前备份`data/backups/20261016-233814`。Excel读取使用Apache POI 5.4.1，CSV使用Apache Commons CSV 1.14.0，版本以pom.xml为准；资料入口：https://poi.apache.org/components/spreadsheet/ 、https://commons.apache.org/proper/commons-csv/ 。

### 居民账户人工合并（2026-10-17）

社区工作人员或社区管理者可在“居民名册”中使用“人工确认账户合并”：选择一条未关联的导入居民记录、选择同社区普通用户账户，并填写核验说明后提交。系统不会仅凭姓名或手机号自动合并，也不允许管理员、普通用户、商家或骑手执行该操作。

合并在一个数据库事务中完成，校验社区归属、居民状态、账户角色和唯一关联；保存合并前姓名、电话、地址、联系人、操作人、原因和时间到`community_resident_merge`历史表；当前生效关联单独保存在`community_resident_merge_current`，使用“社区编号＋居民编号”作为主键并限制一个账户只有一个当前居民关联，名册记录保存`merge_id`和合并状态，审计日志记录`RESIDENT_ACCOUNT_MERGE`。如果目标账户已经有注册来源名册记录，系统保留该注册记录，并将导入记录标记为合并，避免删除注册来源。

合并记录支持“撤销”，必须填写撤销原因。撤销前再次锁定并校验合并ID，只有原合并仍是最后一次变更时才允许撤销；撤销只恢复导入记录的未关联状态，不篡改注册来源资料。撤销会删除当前关联行、保留原历史为`REVOKED`并写入`RESIDENT_ACCOUNT_MERGE_UNDO`审计记录；之后可再次人工核验并生成新的历史记录。重复撤销、跨社区撤销和状态已变化均被拒绝。

新增接口：`GET /api/community/residents/merge/candidates`、`GET /api/community/residents/merge/accounts`、`GET /api/community/residents/merge/history`、`POST /api/community/residents/merge`、`POST /api/community/residents/merge/{id}/undo`。新增12项名册测试中的人工合并、撤销、同社区约束、角色权限、原因校验和审计验证已通过；完整回归结果见`target/merge-regression.log`。

## 手机端禁用说明（2026-10-21）

根据当前部署要求，本项目暂时关闭手机端访问。项目本身没有独立原生 App，手机端原来由响应式 Web、移动 viewport、`@media` 样式和相机拍照入口共同提供。

当前处理如下：

- `src/main/resources/static/app.js` 在初始化前识别常见手机 User-Agent 和小尺寸触摸设备，显示“手机端暂未开放”，不启动登录、订单、通知和照片请求。
- `src/main/resources/static/index.html` 将移动 viewport 保留在 HTML 注释中。
- `src/main/resources/static/style.css` 将 7 组移动端 `@media` 规则保留在 CSS 注释中，桌面布局规则继续生效。
- `app.js` 注释移动相机拍照入口，桌面端普通图片文件上传仍保留。

恢复手机端时，需要同时恢复 viewport、对应 `@media` 规则、相机入口，并移除 `isMobileClient()` 的访问拦截；恢复后必须重新进行真实手机验收。当前没有宣称手机端兼容性或真实手机验收通过。

### 用户配送费与骑手基础收入关联（2026-10-23）
有收费快照的配送订单：骑手基础收入=本订单用户实付配送费，资金来源标记“用户支付配送费”。自取不产生配送收入，0元配送费按已配置0元留档；补贴与扣款仍独立审核。已收费且原骑手快照为“未配置0元”的缺陷记录保留原快照及原流水，使用独立修正表、补记流水和审计修复，一单只补记一次。不自动改写已有非零费率约定，也不向无收费快照的历史订单追收配送费。
部署、实际测试、限制及回滚见 [配送费关联交付记录](docs/courier-fee-link-20261023/delivery.md)。钱包使用模拟资金记账，不代表真实支付或银行转账。
